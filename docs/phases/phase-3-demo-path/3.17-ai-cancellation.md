# 3.17 — Cancel obsolete AI requests

**Branch:** `ahmed/phase-3-ai-cancellation` · **Base:** draft PR #16 at `a70eccd` · **Date:** 2026-09-28 · **Status:** implemented; automated verification passed · **PR:** pending

## Problem and resulting behavior

Stop already prevented obsolete AI replies from editing the frontend, but the synchronous backend provider call could continue in a worker thread after its caller cancelled. This slice makes interpretation and scene explanation asynchronous and ties their local upstream requests to the original request's lifetime. A disconnect or caller cancellation now cancels and awaits the pending operation and its client cleanup.

The same lifetime wrapper covers the phone bridge's authenticated teaching POST routes after body validation. A disconnect reaching that bridge cancels its upstream request and releases its concurrency slot. Its authentication, fixed target, body limit, rate budget, response sanitization and two-request concurrency limit stay unchanged.

## Implementation and decisions

- `backend/ai_request.py` owns one absolute deadline, one operation task and one disconnect receiver. It is called only after the request body is consumed. A blocking ASGI receive works through the bridge's existing middleware; no second consumer polls the same request channel. An observed disconnect wins over an otherwise ready result. Every exit cancels and awaits child tasks, with middleware cancellation shielding for cleanup.
- `main.py` and `scene_analysis.py` use the installed async SDK and async client contexts. The command route retains a 21-second total budget, an initial provider timeout of at most 20 seconds and at most one repair after a validation rejection. Repair starts only with at least six seconds left and uses at most ten seconds or the original remaining budget. Analysis has a 20-second total budget. The bridge retains its 23-second budget.
- Disconnects use a fixed non-success 499 response; deadline failures use fixed 502 messages. Caller cancellation propagates. Existing provider-error mapping, missing-key behavior, source audits, strict request/response contracts and frontend stale-result protection remain.
- No SDK/dependency upgrade, retry policy expansion, model change, prompt change, command authority, mechanics or UI change. Provider storage stays disabled. Existing mocks become asynchronous without removing their assertions.

The deadline bounds pending work; awaiting cooperative client cleanup can extend the final response beyond it. Local cancellation closes local connections; it cannot guarantee that a remote provider stops computation or billing. A deployed gateway must propagate disconnection for this behavior to reach the bridge. No external gateway or real provider was exercised.
